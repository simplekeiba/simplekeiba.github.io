## 1. プロジェクト概要

### 1.1 前提の整理：このサイトが担える役割

新規リスナー獲得において、**Webサイトは主戦場ではない。** ポッドキャストの発見は、その大半が各アプリ内のレコメンド、YouTube、SNS上で起きている。この事実を踏まえずにサイトを作ると、労力に対して成果が出ない。

サイトが現実的に担えるのは、次の3つである。本書はこの3点に集中する。

| 役割 | 内容 | 本書での対応 |
|---|---|---|
| **A. 検索からの入口** | 「競馬 初心者」「◯◯記念 予想」等の検索でエピソードページが拾われる | エピソード個別ページの新設（最重要） |
| **B. 迷わせない着地点** | SNSやYouTubeで番組を知った人が、離脱せず1話目を再生する | 「初めての方へ」導線の新設 |
| **C. 共有される単位** | 1エピソードをSNSでシェアしたとき、内容が伝わる | エピソード別OGP・共有機能 |

逆に、サイトが担えないこと（アプリ内レコメンドの獲得など）はスコープ外とする。

### 1.2 背景：現行サイトの課題

**構造**
- CSSに `.latest-episode-section` `.recommended-episodes-section` `.sense-paddock-section` `.youtube-section` `.contact-section` の定義があるが、対応するHTMLが未実装。**ポッドキャスト番組サイトでありながらエピソードが1本も掲載されていない**
- ナビゲーションがなく1画面スクロールのみ
- 検索エンジンにインデックスされる「中身のあるページ」がトップの1枚しか存在しない。上記の役割Aを構造的に果たせない

**技術**
- `meta description` / OGP / Twitter Card / 構造化データがすべて未実装。**SNSでシェアしてもリンクが素っ気なく表示され、クリックされない**（役割Cの致命的な欠落）
- 日本語サイトなのにフォント指定が `Inter` のみ。日本語グリフを持たずOS依存の表示になる
- 画像ファイル名が日本語。ホスティング環境によりエンコード起因の不具合リスクがある
- `viewport` に `user-scalable=no`。WCAG 2.1 達成基準 1.4.4 に抵触
- 画像が未最適化（WebP化・寸法属性・`loading="lazy"` すべてなし）
- 非推奨の `<center>` タグ、一部 `img` に `alt` なし、著作権表記が `© 2024` のまま

**運用**
- 更新のたびにHTMLを手編集する構造。週次配信では破綻する

### 1.3 目的

**新規リスナーの獲得を最優先とする。**

サイトのゴールは、訪問者に **「配信アプリで1話目を再生させ、フォローさせる」** こと。この一点に全ページを従属させる。

滞直時間を延ばすことは目的ではない。むしろ**速やかにSpotify / Apple へ送り出すことが成功**である。

### 1.4 KPI

| 区分 | 指標 | 初期目標 |
|---|---|---|
| 主要 | 配信プラットフォームへの遷移クリック数 | 月400 |
| 主要 | エピソードページへのオーガニック検索流入 | 月800セッション |
| 補助 | インデックス済みページ数 | 3ヶ月で50ページ以上 |
| 補助 | SNSシェア経由の流入 | 月150セッション |
| 技術 | Lighthouse Performance（モバイル） | 90以上 |

インデックス済みページ数を指標に置くのは、エピソードページの蓄積が検索流入の母数を決めるため。

## 2. ターゲット

### 2.1 プライマリ：競馬に興味はあるが踏み出せていない層

**ペルソナ**：25〜40歳。ダービーや有馬記念の話題は耳にする。友人が馬券を買っているのを見て興味はある。ただし「用語がわからない」「玄人の世界に見える」と感じて入り口で止まっている。

**流入経路**：`競馬 初心者`、`馬券 買い方 わからない`、`競馬 ポッドキャスト` などの検索。またはSNSで流れてきた切り抜き。

**この人が知りたいこと**
1. これは自分向けの番組か（専門家同士の会話ではないか）
2. どの回から聴けばいいか
3. どこで聴けるか

**離脱要因**：専門用語がいきなり出てくる。エピソードが多すぎてどれを選べばいいかわからない。再生までのクリックが多い。

**設計上の含意**：番組名の「難しくない」というPhilosophyは、この層に対する最大の差別化要素である。トップページのファーストビューで最も強く打ち出す。

### 2.2 セカンダリ：競馬は見るが番組を探している層

すでに馬券を買っている。通勤中に聴ける競馬コンテンツを探している。**特定のレース名や馬名で検索して流入する。** エピソード個別ページのSEOが効くのは主にこの層。

### 2.3 ターシャリ：既存リスナー

最新回への到達と、メンバーシップ入会。

**v1.0からの重要な変更：エピソード個別ページをスコープ内に格上げした。**

グローバルナビゲーション：`初めての方へ` / `エピソード` / `番組について` / `メンバーシップ`

ヘッダー右端には **「Spotifyで聴く」ボタンを常時固定表示** する。全ページ・全スクロール位置から1クリックで再生に到達できる状態を保つ。

## 4. ページ別要件

### 4.1 トップ `/`

**このページの唯一の仕事は、3秒で「自分向けの番組だ」と思わせ、再生ボタンを押させること。**

| # | セクション | 要件 |
|---|---|---|
| 1 | ヒーロー | ロゴ、番組名、そして**「難しくない」を明示するキャッチコピー**。配信プラットフォームボタンをファーストビュー内に必ず収める。スクロールさせない |
| 2 | 番組の3行説明 | 何の番組で、誰が話していて、どんなトーンか。専門用語を1つも使わずに書く |
| 3 | 初めての方へ | 3枚のカード。「競馬をやったことがない」「馬券は買うが詳しくない」「レース予想を聴きたい」で入口を分け、それぞれ推奨エピソードへ直結させる |
| 4 | 最新エピソード | RSSから取得した最新1件。再生プレイヤー埋め込み |
| 5 | Philosophy | 既存テキストを流用。トーン維持 |
| 6 | パーソナリティ | 3名。`/about` への導線 |
| 7 | YouTube | 【要確認】チャンネルがあれば最新動画を埋め込む。動画は新規リスナーにとって最も摩擦の少ない入口 |
| 8 | メンバーシップ | 既存バナー＋note.comへの導線 |

**禁止事項**：ファーストビューに情報を詰め込まない。番組名・一言説明・再生ボタン以外は置かない。

### 4.2 初めての方へ `/start` ★

新規リスナーの着地点。SNSやYouTubeから来た人を、ここで確実に再生へ送る。

| # | セクション | 要件 |
|---|---|---|
| 1 | 番組紹介 | 200字程度。「難しくない」の具体的な中身を示す |
| 2 | おすすめの聴き方 | 3タイプ別の入口（トップと同じ分類）。各タイプに推奨エピソード2〜3件 |
| 3 | よく出る用語 | 番組内で頻出する競馬用語を10語だけ、平易に解説。**これ自体が検索流入を生む** |
| 4 | 聴き方 | Spotify / Apple それぞれのフォロー手順を画像付きで。ポッドキャスト自体が初めての人を想定する |

### 4.3 エピソード個別ページ `/episodes/[slug]` ★最重要

**検索流入の主戦場。ページ数がそのまま接点の数になる。**

| 要素 | 要件 |
|---|---|
| タイトル | エピソードタイトル＋番組名 |
| メタ情報 | 話数、配信日、尺、出演者、カテゴリ |
| 再生 | 初回リリースでは埋め込みプレイヤーを設置しない。RSSにSpotifyのエピソードIDが含まれず、番組全体の埋め込みでは常に最新回が再生されるため、記事内容と再生される回が一致しない。代わりに Spotify / Apple のボタンを配置する。Apple は iTunes Search API で取得したエピソードIDにより各回へ直接遷移させる。Spotify は番組トップへ遷移させる。Spotify Web API 導入時に個別埋め込みへ移行する。なお 4.1 のトップページ最新回プレイヤーは維持する。番組全体の埋め込みは常に最新回を再生するため、トップページでは仕様と一致する。Apple の個別エピソードリンクは iTunes Search API の返却上限200件の制約により、新しい順191件のみ対応する。未対応の回は番組トップへ遷移させる。 |
| ショーノート | **本文テキスト。最低500字。** 話題の要約、登場したレース名・馬名・用語 |
| 話題リスト | タイムスタンプ付きの目次 |
| 関連エピソード | カテゴリ分類軸の確定後に実装する。初回リリースでは省略する |
| 共有 | X / LINE への共有ボタン |
| CTA | 「他の回も聴く」→ プラットフォームへ |

**ショーノートの生成について**：全エピソードに手作業で500字を書くのは非現実的である。Whisper等による文字起こしから要約を生成するパイプラインの構築を強く推奨する。これが本プロジェクトで最も投資対効果の高い作業になる。（Python環境での実装が可能。詳細は別途）

構造化データ `PodcastEpisode` を必ず埋め込むこと。

### 4.4 エピソード一覧 `/episodes`

- RSSフィードから全件を自動生成する。手動更新を一切発生させない
- カテゴリによる絞り込み（分類軸は【要確認】）
- 各行：話数、タイトル、配信日、尺、概要抜粋、個別ページへのリンク
- ページネーション。1ページ20件

### 4.5 番組について `/about`

番組の成り立ち、Philosophy拡張版、パーソナリティ3名の詳細プロフィール。

新規リスナー向けに、**3名それぞれの「立ち位置の違い」がわかる書き方**にする。現行の「馬券は直感」「年間1000時間の理論派」という対比は良い素材なので活かす。

### 4.6 メンバーシップ `/membership`

特典内容、料金、入会方法。note.comへ遷移。

### 4.7 スポンサー `/sponsor`（簡易版）

最優先ではないが、機会損失を防ぐため1ページだけ用意する。番組概要、主要な媒体データ、問い合わせ導線のみ。**数値が未確定なら公開時点では省略してよい。**

### 4.8 お問い合わせ `/contact`

種別選択式：`番組への感想・リクエスト` / `出演・取材依頼` / `スポンサー・タイアップ` / `その他`。

### 4.9 秋のGⅠ予想王決定戦 `/yosouou/` ★

リスナー参加企画。対象12レースについて、各レース1頭を指名し、着順に応じてポイントを獲得する（1着5点 / 2着3点 / 3着1点）。応募はフォーム、集計・順位表示はサイトで行う。

#### 4.9.1 位置づけの補正

企画書はこの施策を「サイトへの送客効果 20/20」と評価しているが、**それは既存リスナーをサイトへ動かす効果であって、新規リスナー獲得ではない。** 本プロジェクトの最優先ゴールに接続するには、設計に次の3点を組み込む必要がある。これを外すと、企画は優れたリテンション施策で終わる。

| 施策 | 目的 |
|---|---|
| **参加者個別ページ＋動的OGP画像** | 参加者が自分の順位をXでシェアしたときに「第3位 UMA太郎 18pt」がカード表示される。**これが企画から生まれる唯一の新規流入経路** |
| **途中参加の常時可視化** | 「残り最大◯点」「今からでも逆転可能」を全ページに常時表示。10月以降に知った人が参加をあきらめると、新規獲得の機会が消える |
| **ランキングページからの番組導線** | シェア経由で来た人の大半は番組を知らない。全ページに「Spotifyで聴く」を配置する |

#### 4.9.2 `/yosouou/` 企画トップ

| # | セクション | 要件 |
|---|---|---|
| 1 | 企画概要 | 3行で説明。「毎回1頭選ぶだけ」を最も強く打ち出す |
| 2 | 次の締切 | **次レース名と締切日時を最上部に大きく表示。** 締切超過後は自動で次レースへ切り替わる |
| 3 | 応募ボタン | Googleフォームへ。ページ内に最低2箇所 |
| 4 | 現在の状況 | 参加人数、消化レース数、**残り最大獲得ポイント** |
| 5 | 上位10名 | 順位・ラジオネーム・合計ポイント。`/yosouou/ranking/` へ誘導 |
| 6 | ルール要約 | 5項目以内。詳細は `/yosouou/rules/` へ |
| 7 | 最終更新表示 | 「最終更新：2026年10月19日 19:30（秋華賞終了時点）」形式。**必須** |

#### 4.9.3 `/yosouou/ranking/` 全ランキング

- 全参加者の順位表（項目：順位 / ラジオネーム / 合計ポイント / 1着的中 / 2着的中 / 3着的中 / 参加数）
- その下にレース別実績表。**モバイルでは横スクロール**とし、ラジオネーム列を `position: sticky` で固定する
- 各行から参加者個別ページへリンク
- 同点時の順位表記は同順位とし、次順位を飛ばす（例：1位, 2位, 2位, 4位）

#### 4.9.4 `/yosouou/p/[id]/` 参加者個別ページ ★

**この企画で最も新規獲得に効くページ。**

- URLは連番ID（`p-001` 形式）。**ラジオネームをURLに使わない**（日本語URLの回避、および改名時のリンク切れ防止）
- 表示：ラジオネーム、現在順位、合計ポイント、全レースの指名馬と着順と獲得点
- **動的OGP画像を生成する。** 順位・ラジオネーム・ポイント・番組ロゴを合成した1200×630画像。X共有時にこれが表示される
- 「Xでシェア」ボタン。定型文をプリセットする
- ページ下部に必ず番組の紹介と再生ボタンを置く
- **メールアドレスは一切表示・出力しない**

#### 4.9.5 `/yosouou/rules/` 正式ルール

企画書の内容を掲載する。特に以下を明記すること。

- 締切は**受信時刻基準**（送信時刻ではない）
- 馬名の誤字は運営側で合理的に補正する場合がある
- ラジオネームは公開され、参加者個別ページが自動生成される（**フォームの同意事項にも同一文言を入れる**）
- メールアドレスは本人識別のみに使用し、公開しない
- 本企画は**馬券の購入を必要としない**
- 全12レースの日程と締切一覧（企画書の表を掲載）
- 賞品を用意する場合、購入を条件としない懸賞として扱う。景品表示法上の取り扱いは公開前に消費者庁のガイドラインで確認すること（本書は法的助言ではない）

#### 4.9.6 年末年始の扱い

ホープフルS（12/26）と有馬記念（12/27）は連続開催で、番組の年内最終収録は12月19日。**年内配信では最終順位を発表できない。**

企画書の推奨案（12月28日までにサイトで最終順位発表 → 2027年最初の配信で表彰）を採用する。サイト側の対応は次の通り。

- 12月28日に最終順位ページを公開し、優勝者を明示する
- **サイトが結果発表の一次媒体になる。** この日の更新は落とせない。事前にテンプレートを用意しておくこと

## 5. デザイン要件

### 5.1 方向性

現行のゴールド×ブラックは既存のブランド資産として維持する。ただしグラデーション文字の多用と装飾過多は抑制し、**余白と情報の構造化**で質感を作る。

重要な調整点：黒×ゴールドは「高級・玄人向け」の記号でもある。ターゲットが「敷居が高いと感じている初心者」である以上、**威圧的にならないよう、余白を広く取り、本文は白系で読みやすさを最優先する。**

### 5.2 シグネチャー要素

**エピソード一覧を「出走表」の構造で組む。**

競馬新聞の馬柱が持つ、番号・データ・テキストが高密度に整列した情報美をエピソード一覧に転用する。話数を枠番風のカラーチップで示し、配信日・尺は等幅数字で右揃えにする。一般的なカード型グリッドを避けることで、競馬番組であることが一覧の構造そのものから伝わる。

枠番の8色（白・黒・赤・青・黄・緑・橙・桃）はエピソードのカテゴリ分類にも流用する。競馬ファンには説明不要で伝わり、他のポッドキャストサイトと重複しない配色体系になる。

**ただしトップページと `/start` には持ち込まない。** 初心者にとって出走表は「難しそう」の象徴でもある。この2ページは徹底して平易・開放的に保ち、出走表の意匠はエピソード一覧以降に限定する。大胆さを使う場所は1箇所に絞る。

## 6. 技術要件

### 6.1 スタック

| 項目 | 選定 | 理由 |
|---|---|---|
| フレームワーク | Astro 5.x（`output: 'static'`） | ビルド時にRSSを取得し、エピソード数だけ静的ページを生成できる |
| CSS | Tailwind CSS v4（`@theme` にトークン集約） | セレクタ詳細度の衝突を構造的に防ぐ |
| RSSパース | `rss-parser` | RSSの正規化に最適 |
| 画像 | `astro:assets` | WebP自動生成、寸法属性自動付与 |
| OGP画像生成 | satori + @resvg/resvg-js | astro-og-canvas はレイアウトが固定でロゴ・話数・タイトルの自由配置ができないため変更 |
| SEO | 自前 `<Seo />` ＋ `@astrojs/sitemap` | |
| ショーノート | Content Collections（Markdown） | RSSの説明文では文字数が足りないため別管理 |
| フォーム | Google Forms 埋め込み、または Tally | 静的ホスティングのため |
| 解析 | GA4＋Google Search Console | |

### 6.2 ディレクトリ構成

/
├─ AGENTS.md

├─ src/
│ ├─ components/

ショーノートをRSSと分離するのは、RSSの `description` が短く、SEOに必要な文字量を確保できないため。slugで突合し、ショーノートが未作成のエピソードはRSSの説明文にフォールバックする。

### 6.3 RSS取り込み仕様

- RSSフィードURL: `https://anchor.fm/s/f1b706dc/podcast/rss`
- ビルド時に取得。失敗時はビルドを停止せず、前回取得分のキャッシュJSONで継続する
- 取得項目：`title` `pubDate` `itunes:duration` `itunes:episode` `description` `enclosure.url` `link` `guid`
- slugは `ep-{話数}` 形式を基本とする。話数はエピソードタイトルに含まれる「#」＋半角数字から取得する。RSSの itunes:episode タグは配信側の入力に重複・欠落・誤りがあるため、slugにも話数表示にも使用しない。タイトルに「#」＋半角数字を含まない回に限り、配信日（日本時間）を用いた YYYY-MM-DD 形式とする。同じ日に2本以上ある場合は、配信日時の古い順に末尾へ -2, -3 を付す。話数が重複した場合はビルドを失敗させ、該当回を報告する。一度公開したURLは絶対に変更しない。

### 6.5 ランキングデータの取り込み ★

**前提の確認：本サイトは静的サイトであり、データベースを持たない。** ランキングは「毎週データを流し込んで再ビルドする」構造で実現する。

#### データフロー

Googleフォーム（応募受付）
↓
スプレッドシート［応募データ］ ← メールアドレスを含む。非公開
↓ VLOOKUP等で集計
スプレッドシート［公開用シート］ ← メールアドレスを含まない。CSV公開
↓ ビルド時にfetch
Astro（静的HTML生成）
↓
GitHub Pages

#### 絶対条件

**CSV公開するシートには、メールアドレスを含む列を一切置かないこと。** 応募データシートをそのまま公開する運用は個人情報漏洩に直結する。公開用シートを物理的に別シートとして分離し、参照は関数経由に限定する。これは実装上の最重要制約である。

#### 更新トリガー

- GitHub Actions の `schedule`（cron）で **毎週月曜 20:30 JST** に自動リビルド
- あわせて `workflow_dispatch` を設定し、手動でも即時実行できるようにする（訂正対応用）

#### 最終更新時刻の扱い

**ビルド時刻を「最終更新」として表示してはならない。**

シートが未更新のまま定時ビルドが走ると、順位は変わらないのに更新時刻だけが新しくなる。参加者から見れば「更新されたのに自分の点が入っていない」となり、企画の信頼を損なう。

公開用シートに `updated_at` と `as_of_race`（例：`秋華賞終了時点`）のセルを設け、**その値をそのまま表示する。**

#### フォールバック

CSV取得に失敗した場合、ビルドを停止せず、リポジトリ内のキャッシュJSONで継続する。あわせてページ上に「データ取得に失敗しています」の旨を表示する。**古いデータを何事もなかったように表示しない。**

#### 参加者IDの採番

公開用シートに `participant_id`（`p-001` 形式）列を設け、**一度採番したIDは変更しない。** ラジオネームが変更されてもIDは維持する。IDの振り直しは、共有済みURLをすべて壊す。

## 7. 非機能要件

### 7.1 パフォーマンス

| 指標 | 目標 |
|---|---|
| Lighthouse Performance（モバイル） | 90以上 |
| LCP | 2.5秒未満 |
| CLS | 0.1未満 |
| 総ページ重量（トップ） | 1MB未満 |

新規リスナーの大半はモバイルの検索・SNSから来る。表示速度は直帰率に直結するため、目標値は必達とする。

### 7.2 SEO ★本プロジェクトの中核

**エピソードページの量産が検索流入の母数を決める。** 以下は必須要件とする。

- 全ページに固有の `title`（32文字以内）と `meta description`（120文字以内）
- **エピソードごとの動的OGP画像生成**（話数・タイトル・番組ロゴを合成）。SNSシェア時のクリック率を左右する
- 構造化データ：トップに `PodcastSeries`、エピソード個別に `PodcastEpisode`、`/about` に `Person`、`/start` の用語集に `FAQPage`
- `sitemap.xml` / `robots.txt` を自動生成
- 内部リンク：関連エピソード3件を必ず相互リンクさせる

**狙う検索クエリ**

| 層 | クエリ例 | 対応ページ |
|---|---|---|
| 未経験層 | `競馬 初心者`, `馬券 買い方`, `競馬 用語 わかりやすい` | `/start`、用語集 |
| 未経験層 | `競馬 ポッドキャスト`, `競馬 ラジオ おすすめ` | トップ |
| 経験層 | `{レース名} 予想`, `{馬名}`, `{騎手名}` | エピソード個別 |
| 指名 | `シンプルKEIBA` | トップ |

レース名クエリは検索需要が開催直前に集中する。**該当エピソードは開催週の早い段階で公開し、ショーノートにレース名を明記すること。**

### 7.3 アクセシビリティ

- WCAG 2.1 レベルAA準拠を目標
- `user-scalable=no` は使用しない（現行から修正）
- 本文コントラスト比 4.5:1 以上。**ゴールド（#D4AF37）を黒背景の本文色に使わない**（コントラスト不足）
- 全画像に意味のある `alt`
- キーボードフォーカスを可視化

### 7.4 対応環境

モバイルファースト。ブレークポイント `640 / 768 / 1024 / 1280`。iOS Safari / Android Chrome / デスクトップ主要ブラウザの最新2バージョン。

## 8. インフラ・デプロイ

- GitHubリポジトリ（public）、`main` を本番とする
- GitHub Actions で build → GitHub Pages へデプロイ
- ユーザーページとして公開するため base は設定しない。独自ドメイン simplekeiba.com を使用し、public/CNAME で指定する

- 独自ドメイン simplekeiba.com を2026年7月に取得済み。ただし検索評価はドメイン単位で蓄積されるため、**取得するなら早いほど有利**。後年の移行はリダイレクト設定が必要になり、評価の一部を失う。年額1,500円程度
