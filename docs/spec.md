## 1. プロジェクト概要

### 1.1 前提の整理：このサイトが担える役割

新規リスナー獲得において、**Webサイトは主戦場ではない。** ポッドキャストの発見は、その大半が各アプリ内のレコメンド、YouTube、SNS上で起きている。この事実を踏まえずにサイトを作ると、労力に対して成果が出ない。

サイトが現実的に担えるのは、次の2つである。本書はこの2点に集中する。

| 役割 | 内容 | 本書での対応 |
|---|---|---|
| **B. 迷わせない着地点** | SNSやYouTubeで番組を知った人が、離脱せず1話目を再生する | トップページ「初めての方におすすめ」（FIRST LISTEN）の新設 |
| **C. 共有される単位** | 1エピソードをSNSでシェアしたとき、内容が伝わる | エピソード別OGP・共有機能 |

逆に、サイトが担えないこと（アプリ内レコメンドの獲得など）はスコープ外とする。

### 1.2 背景：現行サイトの課題

**構造**
- CSSに `.latest-episode-section` `.recommended-episodes-section` `.sense-paddock-section` `.youtube-section` `.contact-section` の定義があるが、対応するHTMLが未実装。**ポッドキャスト番組サイトでありながらエピソードが1本も掲載されていない**
- ナビゲーションがなく1画面スクロールのみ
- 検索エンジンにインデックスされる「中身のあるページ」がトップの1枚しか存在しない。上記の役割Aを構造的に果たせない

**技術**
- `meta description` / OGP / Twitter Card / 構造化データがすべて未実装。**SNSでシェアしてもリンクが素っ気なく表示され、クリックされない**（役割Cの致命的な欠落）
- 日本語サイトなのにフォント指定が `Inter` のみ。日本語グリフを持たずOS依存の表示になる
- 画像ファイル名が日本語。ホスティング環境によりエンコード起因の不具合リスクがある
- `viewport` に `user-scalable=no`。WCAG 2.1 達成基準 1.4.4 に抵触
- 画像が未最適化（WebP化・寸法属性・`loading="lazy"` すべてなし）
- 非推奨の `<center>` タグ、一部 `img` に `alt` なし、著作権表記が `© 2024` のまま

**運用**
- 更新のたびにHTMLを手編集する構造。週次配信では破綻する

### 1.3 目的

**新規リスナーの獲得を最優先とする。**

サイトのゴールは、訪問者に **「配信アプリで1話目を再生させ、フォローさせる」** こと。この一点に全ページを従属させる。

滞直時間を延ばすことは目的ではない。むしろ**速やかにSpotify / Apple へ送り出すことが成功**である。

## 2. ターゲット

### 2.1 プライマリ：競馬に興味はあるが踏み出せていない層

**ペルソナ**：25〜40歳。ダービーや有馬記念の話題は耳にする。友人が馬券を買っているのを見て興味はある。ただし「用語がわからない」「玄人の世界に見える」と感じて入り口で止まっている。

**流入経路**：`競馬 初心者`、`馬券 買い方 わからない`、`競馬 ポッドキャスト` などの検索。またはSNSで流れてきた切り抜き。

**この人が知りたいこと**
1. これは自分向けの番組か（専門家同士の会話ではないか）
2. どの回から聴けばいいか
3. どこで聴けるか

**離脱要因**：専門用語がいきなり出てくる。エピソードが多すぎてどれを選べばいいかわからない。再生までのクリックが多い。

**設計上の含意**：番組名の「難しくない」というPhilosophyは、この層に対する最大の差別化要素である。トップページのファーストビューで最も強く打ち出す。

### 2.2 セカンダリ：競馬は見るが番組を探している層

すでに馬券を買っている。通勤中に聴ける競馬コンテンツを探している。**特定のレース名や馬名で検索して流入する。** エピソード個別ページのSEOが効くのは主にこの層。

### 2.3 ターシャリ：既存リスナー

最新回への到達と、メンバーシップ入会。

## 4. ページ別要件

### 4.1 トップ `/` ★v5.0で大幅刷新

**このページの唯一の仕事は、3秒で「自分向けの番組だ」と思わせ、再生ボタンを押させること。** ただし v5.0 では「聴く→参加する→もう1本聴く→番組へ声を送る」という行動導線をトップページ全体で作る方針を追加した。全体構成は上から:

1. **ヒーロー＝ハイライトカルーセル**（4枚構成、詳細は下記）
2. 秋のGⅠ予想王決定戦（詳細カード。企画期間中のみ）
3. 最新エピソード（RSS最新1件＋Spotify埋め込みプレイヤー）
4. **SPECIAL EVENT**（新設）：G1予想企画へのバナー導線
5. **FIRST LISTEN**（新設）：初めての方におすすめエピソード3本
6. **MESSAGE**（新設）：お便りフォームへの導線。ページを締める全幅バンド

#### 4.1.1 ヒーロー＝ハイライトカルーセル

ロゴ・番組名・キャッチコピー・再生ボタンによる静的なヒーローは廃止し、幅は画面いっぱい（ビューポート幅いっぱい）、高さは画像本来の比率（横長バナー、概ね16:9）を保つ横長バナー画像が自動スライドするカルーセルをファーストビューとする。高さをビューポート高さに強制すると、横長画像が縦長の枠に無理やり収まり、特にモバイルで画像内のテキストがほとんど切り取られて読めなくなる不具合が発生したため、v4.2.1で「幅いっぱい・高さは比率に応じて自動」に修正した（大画面では`max-h-[80vh]`程度で上限を設ける）。番組名・再生ボタンは常時固定表示のヘッダー（§3）が担うため、ヒーロー内に別途テキストは置かない。

以下の4パターンを**常時**スライド表示し、各スライドはクリックで遷移先へ移動する（番組紹介パターンは不採用とした）。企画期間外でも4枚とも表示する。

| # | 内容 | 遷移先 |
|---|---|---|
| 1 | メンバーシップ | https://note.com/keiba_podcast/membership （外部リンク、新規タブで開く） |
| 2 | YouTube | https://www.youtube.com/@SimpleKEIBA （外部リンク、新規タブで開く） |
| 3 | 秋のGⅠ予想王決定戦 | /yosouou/ |
| 4 | SENSE PADDOCK（v5.0で追加） | https://www.sense-paddock.com/ （外部リンク、新規タブで開く） |

バナー画像は番組ロゴと同じゴールド×ブラックのトーンを踏襲する。5.3のカラートークン外の色（他社サイト参考にあるような紫・ピンク・黄緑等の背景色）は使用しない。このカルーセルは各遷移先への「導線」を担うのみで、動画データや会員情報そのものは表示しない。

**技術的注意（v5.0で修正した重大バグ）**：スライド自動切替の実装に `Element.scrollIntoView()` を使うと、固定ヘッダー配下のレイアウトでは「要素をビューポート内に収めよう」とするブラウザの判定が**ページ全体（window）のスクロール位置まで動かしてしまうことがある**。ユーザーがページを下にスクロールした状態でも、カルーセルの自動切替のたびにページが上へ引き戻される不具合が発生した。修正は `slides[index].scrollIntoView()` を使わず、トラック要素自身の `scrollTo()` にスライド位置の差分（`getBoundingClientRect()` の差）を渡す方式に変更すること。**横スクロールカルーセルを新規実装する際は、必ずこの方式を踏襲する。**（実装：`src/components/HighlightCarousel.astro`）

**禁止事項**：カルーセルの画像自体にファーストビューの主目的（自分向けの番組だと3秒で伝える）を阻害するような、番組と無関係な内容を新たに追加しない

#### 4.1.2 秋のGⅠ予想王決定戦（詳細カード）

企画期間中（2026年9月〜12月末）のみ表示する。次レース名・締切日時・応募ボタン・現在の参加人数を表示し、/yosouou/ へ遷移させる。企画期間外は非表示にできる構造とする。カルーセル内のスライドとは役割が異なる（カルーセルは視覚的な誘導、こちらは締切・参加人数などの実データ表示）ため、併存させる。

#### 4.1.3 最新エピソード

RSSから取得した最新1件。Spotifyの番組埋め込みプレイヤー（`https://open.spotify.com/embed/show/{id}`）を設置する。番組全体の埋め込みは常に最新回を再生するため、トップページの「最新エピソード」という文脈と一致する（§4.2のエピソード個別ページでは同じ理由から埋め込みを使わない）。**「ショーノートを読む」リンクはv5.0で削除済み**（プレイヤーのみのシンプルな構成に変更）。

#### 4.1.4 SPECIAL EVENT（v5.0で新設）

「番組を聴いた人が、そのままSimple KEIBAの企画に参加する」ための導線。企画の詳細をトップページ上ですべて説明せず、詳細は `/yosouou/` へ誘導する。

構成：セクションラベル「SPECIAL EVENT」→ バナー画像（`special-event-banner.png`、企画タイトルが画像内に含まれる）→ テキストCTA「企画に参加する →」の3要素のみ。**バナー画像自体にはリンクを付けない**（クリック領域はテキストCTAのみに統一）。CTAはゴールドの文字のみで、背景・枠線・ボタン化はしない。

#### 4.1.5 FIRST LISTEN（v5.0で新設）

「初めて聴くならどれか」を示すセクション。セクションラベル「FIRST LISTEN」→見出し「初めての方におすすめ」→補足文→エピソード3本。

- 表示件数は3本固定。5本以上に増やさない（一覧性ではなく「選びやすさ」が目的）
- 各エピソード：サムネイル（RSSの`itunes:image`を使用）、タイトル、配信日＋尺、リンク
- **選定は `src/data/recommendedEpisodes.ts` の配列で管理する。Claude側の判断で自動選定しない。** 空配列の場合は「{{TODO: おすすめエピソード3本の選定}}」がページ上に表示される
- リンク先は**Spotifyの個別エピソードページ**（`spotifyUrl`）。内部の`/episodes/[slug]/`ではない
- モバイルは横型メディアリスト（サムネイル120px＋右にテキスト、1カラム）。デスクトップは3カラムグリッド（サムネイルは正方形、カード幅いっぱい）

#### 4.1.6 MESSAGE（v5.0で新設、リスナーとの交流導線）

ページを締める、全幅の帯セクション（`bg-ink-raised`、`border-t border-ink-line`）。「問い合わせフォームへの案内」ではなく「番組を締める静かなCTA」として設計する。

- 文言：ラベル「MESSAGE」→見出し「あなたの声を、番組へ。」（2行固定）→本文「感想・質問・テーマのリクエストなど、お便りをお待ちしています。」→CTA「お便りを送る →`
- リンク先：`https://forms.gle/gzB6HPzrPfmxv5Kq8`（`MESSAGE_FORM_URL`、新規タブ）
- デスクトップは2カラム（左：ラベル＋見出し、右：本文＋CTA、50:50、max-width 1140px中央配置）。モバイルは1カラム
- 封筒アイコン・ゴールド背景ボタン・カードUI・グラデーションは使用しない。CTAは背景・枠なしのテキストリンクのみ
- 背景色について：依頼時は「ページ本体よりわずかに明るい黒（#0D0E10前後）」という指定だったが、これはカラートークン外の新色になるため、既存トークン `--ink-raised`（#15151A）で代用した。**より正確な色差が必要な場合は、新トークンとして§5.3に追加する前にYusukeの確認が必要**（§13参照、未解決）

※旧セクションの「番組の3行説明」「初めての方へ（3枚カード）」「Philosophy」「パーソナリティ」は削除し、それぞれ /about と /personality に集約する。

### 4.2 エピソード個別ページ `/episodes/[slug]`

| 要素 | 要件 |
|---|---|
| タイトル | エピソードタイトル＋番組名 |
| メタ情報 | 話数、配信日、尺、出演者、カテゴリ |
| 再生 | 初回リリースでは埋め込みプレイヤーを設置しない。RSSにSpotifyのエピソードIDが含まれず、番組全体の埋め込みでは常に最新回が再生されるため、記事内容と再生される回が一致しない。代わりに Spotify / Apple のボタンを配置する。Apple は iTunes Search API で取得したエピソードIDにより各回へ直接遷移させる。Spotify は番組トップへ遷移させる。Spotify Web API 導入時に個別埋め込みへ移行する。なお 4.1 のトップページ最新回プレイヤーは維持する。番組全体の埋め込みは常に最新回を再生するため、トップページでは仕様と一致する。Apple の個別エピソードリンクは iTunes Search API の返却上限200件の制約により、新しい順191件のみ対応する。未対応の回は番組トップへ遷移させる。 |
| ショーノート | RSSの説明文を表示する。補足が必要な回のみ個別に追記する |

## 5. デザイン要件

### 5.1 方向性

現行のゴールド×ブラックは既存のブランド資産として維持する。ただしグラデーション文字の多用と装飾過多は抑制し、**余白と情報の構造化**で質感を作る。

重要な調整点：黒×ゴールドは「高級・玄人向け」の記号でもある。ターゲットが「敷居が高いと感じている初心者」である以上、**威圧的にならないよう、余白を広く取り、本文は白系で読みやすさを最優先する。**

**v5.0で全ページに共通して適用した追加の禁止事項**（`/yosouou/`のブランドブリーフを起点に、他ページにも波及させた基準）：王冠・トロフィー・メダル・キラキラ・光彩・派手なグラデーション・馬の装飾イラスト・不要なマイクアイコン・厚いゴールドの囲み枠・ホバーで大きく浮くカードUI・封筒アイコン等の紋切り型装飾は、いずれのページにも新規追加しない。「装飾で格好良く見せる」のではなく「タイポグラフィ・整列・余白だけで成立させる」ことを優先する。

### 5.2 シグネチャー要素

**（v5.1で撤回）** v5.0までは「エピソード一覧を『出走表』の構造で組む」ことをシグネチャー要素としていた（話数を枠番風カラーチップで表示、左端に太い色分けライン、等幅数字の右揃えなど）。v5.1で、200本を超えるエピソード数に対してこの意匠が「管理画面・データベースの更新履歴」のように見え、番号が主張しすぎてタイトルとの視覚的優先順位が逆転しているという指摘を受け、`/episodes` を通常のポッドキャストアーカイブに近い、余白ベースのリストデザインへ変更した（§4.3）。枠番カラーの8色トークン自体（§5.3）は撤廃していないが、エピソード一覧での使用は取りやめている。将来カテゴリ分類機能を実装する際に再利用するかは未定。

**トップページ・`/about`・`/personality`・`/yosouou/`に出走表的な意匠（枠番カラー・カード多用・太いライン）を持ち込まない方針は変更なし。**

### 6.3 RSS取り込み仕様

- RSSフィードURL: `https://anchor.fm/s/f1b706dc/podcast/rss`
- ビルド時に取得。失敗時はビルドを停止せず、前回取得分のキャッシュJSONで継続する
- 取得項目：`title` `pubDate` `itunes:duration` `itunes:episode` `description` `enclosure.url` `link` `guid` `itunes:image`（v5.0で追加。エピソードサムネイル用。実体はRSS全体で2種類の画像しかなく、番組アートワークの使い回しに近い）
- slugは `ep-{話数}` 形式を基本とする。話数はエピソードタイトルに含まれる「#」＋半角数字から取得する。RSSの itunes:episode タグは配信側の入力に重複・欠落・誤りがあるため、slugにも話数表示にも使用しない。タイトルに「#」＋半角数字を含まない回に限り、配信日（日本時間）を用いた YYYY-MM-DD 形式とする。同じ日に2本以上ある場合は、配信日時の古い順に末尾へ -2, -3 を付す。話数が重複した場合はビルドを失敗させ、該当回を報告する。一度公開したURLは絶対に変更しない。

### 6.5 ランキングデータの取り込み ★

**前提の確認：本サイトは静的サイトであり、データベースを持たない。** ランキングは「毎週データを流し込んで再ビルドする」構造で実現する。

#### データフロー

Googleフォーム（応募受付）
↓
スプレッドシート［応募データ］ ← メールアドレスを含む。非公開
↓ VLOOKUP等で集計
スプレッドシート［公開用シート］ ← メールアドレスを含まない。CSV公開
↓ ビルド時にfetch
Astro（静的HTML生成）
↓
GitHub Pages

#### 絶対条件

**CSV公開するシートには、メールアドレスを含む列を一切置かないこと。** 応募データシートをそのまま公開する運用は個人情報漏洩に直結する。公開用シートを物理的に別シートとして分離し、参照は関数経由に限定する。これは実装上の最重要制約である。

#### 更新トリガー

- GitHub Actions の `schedule`（cron）で **毎日 19:30 JST** に自動リビルド
- あわせて `workflow_dispatch` を設定し、手動でも即時実行できるようにする（訂正対応用）

§8 のRSS自動リビルドと統合し、cronを1本にまとめる。また §12.2 のランキング更新期限（月曜20:00）より前に完了させる必要があるため、20:30では構造的に遅刻する。

#### 最終更新時刻の扱い

**ビルド時刻を「最終更新」として表示してはならない。**

シートが未更新のまま定時ビルドが走ると、順位は変わらないのに更新時刻だけが新しくなる。参加者から見れば「更新されたのに自分の点が入っていない」となり、企画の信頼を損なう。

公開用シートに `updated_at` と `as_of_race`（例：`秋華賞終了時点`）のセルを設け、**その値をそのまま表示する。**

#### フォールバック

CSV取得に失敗した場合、ビルドを停止せず、リポジトリ内のキャッシュJSONで継続する。あわせてページ上に「データ取得に失敗しています」の旨を表示する。**古いデータを何事もなかったように表示しない。**

#### 参加者IDの採番

公開用シートに `participant_id`（`p-001` 形式）列を設け、**一度採番したIDは変更しない。** ラジオネームが変更されてもIDは維持する。IDの振り直しは、共有済みURLをすべて壊す。

- `<link rel="canonical">`：`Astro.site` と `Astro.url.pathname` から自動算出
- `og:type`（`website` 固定）、`og:site_name`（`Simple KEIBA` 固定）、`og:locale`（`ja_JP` 固定）、`og:url`（canonicalと同一）
- `og:image:width` / `og:image:height`（1200×630固定、既存の画像がすべてこのサイズのため）、`og:image:type`（`image/png` 固定）、`og:image:alt`（`ogImageAlt` prop、未指定時は `title` を流用）

### 13.5 技術的な注意点まとめ（このセッションで踏んだ地雷）

- **カルーセルの`scrollIntoView()`問題**（§4.1.1）：固定ヘッダー配下で使うとページ全体がスクロールする。`scrollTo()`に統一済み
- **`.gitignore`の`*.png`一括除外**（§6.4）：新しい画像アセットが気づかずGit管理外になる。`src/assets/*.png`と`public/favicon*.png`等に個別で例外を追加済みだが、新しいディレクトリに画像を置く際は要注意
- **`npm run build`の並行実行競合**（§13.2の8番）：短時間に連続実行すると`dist/.prerender`が壊れることがある。単発では再現しない
- **画像内蔵テキストの見切れ**（v4.2.1で修正済みだが再発しやすい）：横長バナー画像をビューポート高さに強制すると、モバイルで画像内テキストが切れる。高さは常に画像比率に応じて自動にすること（`aspect-video`等）、または`object-contain`で切り取らない設計にする
- **添付画像の実ファイルパスが不明な場合**：チャットに貼られた画像だけでは実体を取得できないことがある。ユーザーに`C:\dev\simple-keiba`直下へファイルを置いてもらい、`find`コマンド等で発見してから`src/assets/`へ`mv`する運用が定着した
- **【v5.1で新規】satoriで使う組み込みフォント（`ZenKakuGothicNew-Bold.ttf`／`NotoSansJP-Regular.ttf`）はどちらもサブセットで、全角チルダ「～」等の一部記号のグリフを含まない**（§7.2）。動的OGP生成でこの2書体以外の文字（絵文字・記号・稀な約物など）を扱う場合は、事前にGoogle Fonts CSS2 API（`https://fonts.googleapis.com/css2?family=...&text=...`）で対象文字を含むサブセットを取得して差し替えるか、事前レンダリングした静止画に切り替えることを検討する
- **【v5.1で新規】`astro dev`はプロジェクト単位で二重起動できない**（§13.2の10番）。ブラウザ検証で「別セッションのdevサーバーがポートを使用中」と出た場合、別ポート指定では解決しない。`astro build && astro preview --port <port>`に切り替える
